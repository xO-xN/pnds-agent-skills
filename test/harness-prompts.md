# External workflow requests

Create fresh raw materials with `node scripts/create-harness-fixtures.mjs <new-directory>`. Copy just the selected published Skill directory to the evaluator's isolated directory. Supply the target App location and version, or a versioned manual checkout; do not silently substitute a maintainer installation. For module integration also supply the actual matching released QR directory. The evaluator sees the realistic request and raw inputs, not implementation conclusions. Keep native/browser/phone/audio conditions truthful.

1. **New work — pnds-create**: “Create a visual-only PNDS source project in `<output>`: one monitor has a cyan bar that advances over twelve seconds after visible START, then stops; performer page only displays an observation instruction. I choose None audio and local use. Use the supplied target App/manual version. I want editable source and an accurate handoff, and will open/test it in the App myself. Do not distribute it yet.”
2. **Existing modification — pnds-create**: “In `<fixtures>/existing-project`, complete the existing caption handoff task. Keep this work's behavior and give me the source and checks performed. Use the supplied target App/manual.”
3. **Non-triple conversion — pnds-port**: “Assess `<fixtures>/browser-source` for a PNDS version. Preserve its sound and timed visual behavior. I haven't chosen the audio implementation and only want an assessment and concrete proposal first.” After the actual proposal, the human confirms a specific route and any necessary artistic changes before the evaluator continues. Do not prefill a generic yes or infer it from this prompt.
4. **Partial source — pnds-investigate**: “Investigate `<fixtures>/partial-source` and report what can actually be established, what I should provide next and why. Do not convert it yet.”
5. **Independent author discussion — pnds-assess**: “I have only the partial-source description. I want a PNDS work on a Mac without the original Max installation, retaining eight output channels and gesture behavior. Assess practical routes and what remains undecided; do not implement.”
6. **Independent runtime — pnds-runtime**: “Audit `<fixtures>/existing-project` against the supplied target App manual. Report necessary structure/runtime corrections and separate what can be statically checked from actual App opening. This is an audit, not permission to change artistic content.” A separately authorized adaptation can follow without resetting identity.
7. **Independent modules — pnds-modules**: “Wire the supplied fixed QR module into `<fixtures>/existing-project` so the monitor QR and label point to the actual performer URL. I authorize the route/import/page changes needed for that capability. Preserve existing identity, source decisions and captions; verify its public interfaces and report page/native checks you could not perform.” For a conflict task, supply an actual customized QR file/provenance and request comparison before an upgrade.
8. **Independent validation — pnds-validate**: “Check and hand off `<fixtures>/existing-project` as editable source only. Explicit None-mode smoke on a copied runtime is authorized; no distribution is requested.” For distribution, follow with: “Now generate a .pnds in `<distribution-output>` from the saved source, report SHA256 and archive checks. I will perform the native install round trip.”
9. **Explicit CM1 — pnds-cm1**: “Use CM1 to examine `<fixtures>/cm1-source` for the course first phase. Tell me whether this is sufficient course input and what decisions are missing before implementation.” This synthetic partial triple covers the retained course gate, not a completed polished course regression. A full course run needs an actual polished triple, actual author confirmation, compiler/assets, protocol/recovery, None health, browser cold/warm and M/P audit; real phones/sound/native acceptance must be observed separately.

For each run retain harness/version, model identifier if exposed, raw inputs, corpus/App/module evidence, author confirmation, artifacts, checks, result and limitations. Check outcomes through files, actual commands/public runtime interfaces and observed operations. Do not score matching sentences or the evaluator's internal reasoning. Source hashes before/after an assessment establish whether premature rewriting happened.
