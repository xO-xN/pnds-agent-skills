# Discuss and assess / 作者讨论与可行性

Input: an investigation report, source material, or author goal, and the target App/deployment facts available. Output: feasibility report, candidate routes, unresolved decisions and a concrete implementation proposal. Done for assessment: report delivered. Done for proceeding: the author has explicitly confirmed the proposal's scope.

Use [platform-sources](../reference/platform-sources.md) and [records](../reference/records.md). If evidence is partial, distinguish source facts, platform limitations, suggestions and open questions. Outcomes can be feasible, conditionally feasible, needs further validation or presently infeasible. Any source can be assessed; conversion is not guaranteed.

Default to preserving sound, visual meaning, interaction and performance timing equally. Language, file organization and transport can change under the proposed adaptation. Do not impose a general fidelity ranking, Internal/External/None mode, local/telematic topology, hub, role/seat or voice policy. Derive alternatives from this work, the installed platform and the author's deployment goal.

Present a proposal before rewriting: target structure/runtime, chosen audio mode and network route, intended module use, behavior preserved, necessary artistic changes with reasons, risks, missing conditions and initial delivery scope. Each necessary sound/visual/interaction/time change belongs to the author. A missing fact remains unresolved rather than becoming a technical default.

Stop before implementation until author confirmation is present. A prior explicit authorization covering the concrete current proposal remains valid; do not repeatedly ask for confirmed choices. Record the actual confirmation and its scope. A pure assessment task ends with the report; it need not produce a PNDS project or bundle. Follow-up implementation reads the same decisions and unresolved items.
